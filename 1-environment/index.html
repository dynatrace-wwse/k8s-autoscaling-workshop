    1. Check the Environment#

    Your environment already runs everything the upstream workshop's bootstrap built: a Kubernetes cluster, the Dynatrace Operator with a DynaKube, an OpenTelemetry Collector and opentelemetry-demo-light under constant load from k6. This step makes sure all of it is up before you start optimizing.

    The demo application#

    Look at the eight workloads of the demo, and at the resources each container requests:

    kubectl get pods -n otel-demo
kubectl get deployments,statefulsets -n otel-demo \
  -o custom-columns='WORKLOAD:.metadata.name,CPU REQUEST:.spec.template.spec.containers[0].resources.requests.cpu,MEMORY REQUEST:.spec.template.spec.containers[0].resources.requests.memory'

    Every workload requests a little memory and no CPU at all. The scheduler places pods by their requests, so these numbers decide how many pods fit on a node — whatever the pods actually use. Keep this table in mind: in step 4 you replace these guesses with numbers measured by Dynatrace.

    Each workload also carries the annotation resource-optimization.dynatrace.com/enabled: "true". That is the opt-in the optimizer looks for — workloads without it are never touched:

    kubectl get deployment cart -n otel-demo -o jsonpath='{.metadata.annotations}' ; echo

    The OpenTelemetry Collector#

    The demo's services are instrumented with OpenTelemetry and send OTLP to a collector in namespace otel-collector. It runs as a DaemonSet — one collector per node — because besides OTLP it also reads every container's log files from the node it runs on (/var/log/pods, the filelog receiver). Look at its pipeline:

    kubectl get ds -n otel-collector
kubectl get cm otel-collector-config -n otel-collector -o jsonpath='{.data.config\.yaml}' | grep -A3 'pipelines:' -m1 ; \
kubectl get cm otel-collector-config -n otel-collector -o jsonpath='{.data.config\.yaml}' | sed -n '/^    logs:/,/exporters/p'
    • k8sattributes adds the pod, workload and namespace — and the resource-optimization annotation — to every span, metric and log.
    • cumulativetodelta converts cumulative counters to the delta temporality Dynatrace ingests.
    • otlp_http exports to your Dynatrace tenant with an ingest token that never left the cluster's Secret.

    Dynatrace in the cluster#

    The Operator deployed a DynaKube in Kubernetes monitoring mode: an ActiveGate watches the Kubernetes API and reports the cluster, its workloads and every container's CPU and memory usage and requests to Dynatrace. Nothing is injected into the demo pods — they are observed through OpenTelemetry only.

    kubectl get dynakube -n dynatrace
kubectl get pods -n dynatrace
